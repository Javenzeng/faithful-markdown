Human real-machine H1 Cold Start failed on the first cold restart after one successful source launch. The app became `Markdown Reader & Editor (未响应)` and PowerShell reported pywebview traversal under `window.native.AccessibilityObject.Bounds.Empty.Empty...` followed by `maximum recursion depth exceeded`. H2-H7 were stopped. V2.1 is not Windows accepted.

## 2. Root-cause verification

Project dependency is `pywebview==6.2.1`. The exact 6.2.1 source at:

`https://raw.githubusercontent.com/r0x0r/pywebview/6.2.1/webview/util.py`

confirms `inject_pywebview()` -> `get_functions()` behavior:

- it iterates `dir(obj)`;
- names starting with `_` are skipped before `getattr`;
- public methods/functions are exposed;
- public class or non-callable object attributes with `__module__` are recursively passed back to `get_functions()`.

Current pre-fix `EditorAPI` had:

- public `self.window: webview.Window | None`;
- `bind_window()` assigning the full `webview.Window` to that public attribute.

Therefore after binding, pywebview discovery can traverse `api.window` recursively into the Window object graph. `webview.Window` itself exposes public `native`, and the Human Windows trace shows exactly that traversal continuing into the WinForms/native Accessibility object graph. The root-cause chain is supported by the exact dependency source and the real-machine trace.

This is also consistent with pywebview issue #1442, where a public non-callable `ConfigParser` attribute is recursively entered by the same `get_functions()` path.

Conclusion: root cause CONFIRMED with high confidence. No speculative fallback fix was needed.

## 3. Minimal fix

Only `app.py` runtime code changed:

- `self.window` -> `self._window`;
- `bind_window()` now stores the reference in `_window`;
- `open_file()` and `save_as()` use `_window` internally.

No EditorAPI redesign, wrapper, second API object, retry, timeout, sleep, watchdog, recursion-limit change, monkey patch, fallback, compatibility shim, or dependency was added.
